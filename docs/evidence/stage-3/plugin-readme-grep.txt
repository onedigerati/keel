9:| `/keel:plan` | Creates or updates `docs/PLAN.md`: goal, current position, stages with acceptance checks and a risk line, dated decisions, open questions. Each check names its proof: a test wherever a test can cover it, otherwise the reason it can't. Adopts an existing plan file instead of starting a second one. In a repo that already has code, it first surveys the part the plan touches and records a test baseline. When a plan's goal is met, it starts the next plan (see below), moving the old plan's evidence beside its archive. |
10:| `/keel:stage` | Runs the next stage: scope, build (independent parts fanned out to subagents in their own worktrees), test, verify, review, update the plan, commit (the stage's evidence included), then stop for your review. Before deciding on review, it checks the risk line against what the diff actually touches and corrects it in the plan when it's wrong. The report links the stage's evidence. |
11:| `/keel:autopilot` | Autopilot: Claude takes over an approved plan as project manager and runs every remaining stage without stopping between them. Builders are subagents; the manager verifies (or has a fresh agent verify, writing the stage's evidence), reviews, commits and keeps the plan current. It rechecks each stage's risk line against the diff as `/keel:stage` does. The final report links each stage's evidence report. It pauses before stages that touch auth, money or personal data (including a stage whose corrected risk line names them, before closing it), on decisions only you can make, on checks it can't get green, and before anything outward-facing (push, deploy, real data). |
12:| `/keel:verify` | Type check, lint, tests, build and a dependency audit, then each acceptance check proven in the running product. At the plan's last stage, it also re-runs the earlier stages' checks that weren't proven by a test, so a later stage can't break one unnoticed. On a request only for a report, it reports failures and leaves them. For a plan stage, it saves a per-check report and the output behind it to `docs/evidence/stage-<n>/` (see [Evidence](#evidence)). |
13:| `/keel:review` | A fresh-eyes review by an agent that didn't write the code, with a security pass for risky stages, judged by the risk line as corrected against the diff. Findings are verified and sorted into fix, defer or reject. |
21:2. **Build.** Step through the stages with `/keel:stage`, stopping after each for your review, or hand the plan to `/keel:autopilot`. Each stage is verified against the running product, reviewed when risky (by the risk line as checked against the diff, not only as planned), and committed with its evidence in `docs/evidence/stage-<n>/`. Verifying the last stage also re-runs the earlier stages' checks not proven by a test. Untested code gets a test of its current behavior before it changes.
28:- **Autopilot stops, enforced.** While autopilot is armed: outward-facing commands are blocked (`git push`, package publishes, deploys, `gh` writes, requests that send data to an outside host); a stage whose risk line names auth, money or personal data gets no file edits outside the plan and no builder agents until you reply. In every mode, a commit that ticks a stage whose `## Now` checks were never seen ticked is refused.
29:- **Evidence gate.** In every mode, a commit that ticks stage n in the plan is refused unless `docs/evidence/stage-<n>/report.md` is in the commit or the working tree and its first table has a row for each of the stage's checks. Rows for re-runs of earlier stages' checks (`Re-run of stage <k>: …`) don't count toward them. The check count comes from what this session saw of `## Now`, or from the plan at HEAD when the session never saw that stage; the ticked-checks gate uses the same fallback. This applies to stages of plans started before 0.5.0 too, and the refusal says how to backfill a report. The gate only checks that a report is there and covers every check, not that the evidence is any good; that stays with verify and review. Its limits:
39:- `report.md`: a table with a row per acceptance check (check, pass or fail, and a link to the proof), the commit it was verified on, and a History of earlier failures and their fixes. A failing check is recorded as fail. At the plan's last stage, each re-run of an earlier stage's check gets its own row after those, as `Re-run of stage <k>: <check>`.
