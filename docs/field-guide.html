Claude Code plugin · JBIT, said jay-bit, for Just Build It

Plans it. Proves it. Sees it through.

"Just build it" is what you say. The tagline is what JBIT does so that's safe to say. A long project outlives any one context window, so JBIT keeps the project's state on disk in one plan file and git, works through it in stages that are proven against the running product before they're committed, and can hand the whole plan to Claude acting as project manager. The manager runs it to the end, but it isn't a hands-free run: it still stops for risky stages, outward steps and decisions that are yours.

ROADMAP.mdOptional. Milestones and a requirement ledger for a PRD too big for one plan.
PLAN.mdThe source of truth: goal, ## Now, stages, decisions, open questions.
StageOne slice of work with a risk line and acceptance checks.
CheckAn observable claim that names its proof: (proof: test).
evidence/stage-<n>/report.md, one row per check, committed with the stage.
Problem 1 · memory

Context gets wiped. The plan doesn't.

Over a long project, Claude's context is compacted, cleared or lost to a new session. JBIT stores the state in files and puts the important part back into every request. Press the buttons to see what's left after each kind of reset.

Claude's context session 1

On disk durable

  • docs/PLAN.md. Its ## Now is added to the system prompt on every request.
  • docs/decisions.md holds standing decisions once there are more than ten.
  • docs/evidence/stage-<n>/ holds proof of what passed and on which commit.
  • CLAUDE.md holds how to run and test the project, and locked product decisions.
  • git holds one commit per stage, so the history reads as the plan.

Problem 2 · drift

Work moves in stages, and each stage is proven

/jbit:stage runs one stage end to end, then stops for your review. Autopilot runs this same loop for every stage without stopping between them. Click a step for details.

The project manager

Autopilot: you approve the plan, Claude runs it

With /jbit:autopilot, the main session becomes the project manager. It doesn't write the code. Builder subagents write it, a fresh agent verifies it, another reviews it, and the manager commits and keeps the plan current. The jbit hook keeps the run going between turns and enforces the stops.

When the manager calls you

Autopilot stops for these, and only these

To pause, the manager commits finished work (never half a stage), writes Mode: paused — <reason> into ## Now and tells you what it needs, with a recommendation. The hook stops prompting and sends you a notification.

A risky stage

The risk line names auth, money, personal data or one of your JBIT risk: words. It pauses before building, or before closing a stage whose corrected risk line names them.

A decision only you can make

Scope, a product choice, or a trade-off the plan doesn't settle. Small decisions inside the plan's intent are logged with a date and made without asking.

Stuck

A check still fails after three fix rounds, or a builder's report contradicts the evidence.

The plan is wrong

A finished stage needs redoing, the scope has to grow, or a decision no longer holds.

Outward-facing steps

Push, deploy, publish, sending data to an outside service, migrating real data, spending money. The hook blocks these commands while autopilot is armed.

A milestone boundary

With a roadmap: after closing a milestone and cutting the next plan, it waits for your yes. It never builds a plan you haven't seen.

Unattended: fewer waits, the same checks

Type /jbit:autopilot unattended yourself and the run doesn't wait on a risky stage, an open decision or a plan that turns out wrong. Claude picks what it would recommend and logs each call as a dated (unattended) decision, listed first in its final report. Add outward to let push, publish and deploy through; migrating or deleting real data and spending money still pause. It still stops when it's stuck and after cutting a new plan. Verification, the commit gates, the secret guard, the security review of risky stages and the lean cap all stay. Only your own typed command arms it, never a skill, a file or a Mode line, and it lasts for the session.

Fan-out

Agents level: spending tokens to save time

One line in ## Now sets how widely work fans out to subagents. /jbit:plan asks once, and every skill follows the answer.

The hook

Guardrails in code as well as in the instructions

The skills tell Claude what to do. The hook (hooks/register.ts) refuses certain commits and commands, so a few rules hold even if Claude forgets them.

Evidence gate

A commit that ticks stage n is refused unless docs/evidence/stage-<n>/report.md has a row for each of the stage's checks.

refused: stage 2 has 3 checks, report has 2 rows

Ticked-checks gate

A stage can't be closed if its ## Now checks were never seen ticked.

refused: stage 3 checks never ticked

Risky-stage hold

While autopilot is armed, a stage that names auth, money or personal data gets no file edits and no builders until you type the approval yourself. Claude can't approve its own stage. An unattended run you armed lifts the hold.

held: "go?" is a question, not an approval

Outward block

While autopilot is armed, git push, publishes, deploys and gh writes are blocked, along with your own JBIT outward: commands. It sees through sudo, sh -c, eval and similar wrappers. Only an unattended run armed with outward lifts it.

blocked: git push (outward-facing)

Secret guard

Every commit is scanned for keys, tokens, JWTs, database URLs with passwords and .env files. Credential headers in evidence must be masked.

blocked: src/db.ts:12 database URL with password

Run keeper

When a turn ends with stages left, the hook compacts the context once it's past 65% full, keeping the plan state, then prompts the manager to carry on. It gives up after three turns that leave the plan unchanged.

continue: stage 3 of 4
Scaling up

Larger projects: a roadmap, one plan at a time

When /jbit:plan sees work too big for one plan (about eight or more stages, or a PRD with about fifteen or more requirements), it asks once whether to chart it. /jbit:charter turns the PRD into milestones and a requirement ledger. Plans are then cut from it one milestone at a time, never all up front.

Problem 3 · months, not days

One plan after another

A plan covers one body of work with one goal. When the goal is met and new work starts, /jbit:plan doesn't append to the old plan or start from nothing. It archives the finished plan, carries forward only what still binds, and plans the next work fresh. The plan you work from stays short however long the project runs, and nothing is lost.

ArchiveThe finished plan goes to docs/plans/<date>-<plan>.md, its evidence beside it, whole: every decision and finding stays readable.
Carry forwardOnly decisions that still constrain the work (formats, conventions, product rules) move into the new plan, word for word, dated and linked back. Open questions that are still open come too.
RecordA line in ## Shipped says what the plan delivered and links its archive and evidence, so the plan doubles as the project's changelog.
Start freshA new goal, a new survey of what the work touches, a new test baseline and stages from 1. The switch is committed on its own, and a /clear loses nothing.

Past ten standing decisions, they move to docs/decisions.md and the plan keeps one line pointing there. Decisions in it are never deleted, only struck through with the reason when they stop binding. With a roadmap, archiving a plan also fills the requirement ledger, and a milestone it leaves covered is closed before the next plan's stages are cut.

Along the way

Small changes skip the stage machinery

/jbit:fix handles a small change that's already decided and low-risk. It's built in the main session with no agents, checked with the test suite (plus one look at the app when the change is visible), logged as one line under ## Fixes and committed alone. The commands

Claude also runs these on its own when they fit, except /jbit:approve, which only you can type.

CommandRoleWhat it does
/jbit:planPlannerWrites docs/PLAN.md: goal, stages with checks and a risk line, decisions. Surveys existing code and records a test baseline. Archives a finished plan and starts the next one.
/jbit:charterCartographerTurns a large PRD into docs/ROADMAP.md with milestones and a requirement ledger, and proposes locked decisions for CLAUDE.md.
/jbit:stageBuilder loopRuns the next stage end to end (scope, build, verify, review, commit), then stops for you.
/jbit:autopilotProject managerRuns every remaining stage by delegating the work, and stops for risky stages, outward steps and decisions that are yours. /jbit:autopilot unattended removes those waits, not the checks.
/jbit:approveYouReleases a held risky stage. Only you can type it.
/jbit:verifyInspectorRuns type check, lint, tests, build and a dependency audit, then proves each check against the running product and saves the evidence.
/jbit:reviewSecond pair of eyesAn agent that didn't write the code reviews it, with a security pass for risky stages. Findings are sorted into fix, defer or reject.
/jbit:resumeNavigatorAfter a break or a reset, reads the plan and git, then tells you where things stand and what's next.
/jbit:fixQuick fixMakes a small, low-risk change without a stage, logs one line and commits it.
