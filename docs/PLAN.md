# Keel plan

## Goal
Let the user choose how widely Keel fans work out to subagents, trading tokens for wall-clock time. Today the skills leave it to the model ("can go to subagents", "several at once"), so a user who wants a project done fast, or one watching cost, has no lever but to repeat it in prompts. Done looks like this: an `Agents: lean | balanced | wide` line in the plan's `## Now`, set when planning or changed any time, that stage, autopilot, review and verify follow; the level rides in every request and shows in the status line; `lean` is held to one running agent by the hook; a `wide` line left from an earlier session isn't honoured until the user confirms it; and evals show lean building inline and wide fanning out. Shipped as keel 0.7.0.

## Decisions
- 2026-11-08 · Three levels: `lean` (build and verify in the main session, one agent at a time), `balanced` (today's behaviour, and the default when there's no line), `wide` (fan out every independent leaf in its own worktree, a fresh agent verifies, correctness and security reviewers run in parallel) — named levels are easier to say and remember than a number, and `balanced` keeps existing projects unchanged.
- 2026-11-08 · The level lives in `## Now` as `Agents: <level>`, beside the Mode line, and the skills carry it into each new `## Now` — the hook already reads `## Now` into every request, so the level survives compaction with no new file or setting.
- 2026-11-08 · Every level keeps at least one fresh reviewer — review by an agent that didn't write the code is the point of `keel:review`, and `lean` is about parallelism, not about skipping independent eyes. Under `lean`, autopilot still delegates building, one builder at a time.
- 2026-11-08 · A `wide` line already in the plan when a session starts counts as `balanced` until the user confirms; Claude confirms by restamping the line (`Agents: wide — confirmed 2026-11-08`), and the hook honours a line that changed during the session, as it does for Mode — a cloned repo shouldn't raise the user's spend unasked. `lean` and `balanced` are honoured as found, since they only lower it.
- 2026-11-08 · Only `lean` gets a hard cap (one running agent); `balanced` and `wide` aren't capped by Keel — a cap on `balanced` would change today's behaviour, and Claude Code's own limits already bound `wide`.
- 2026-11-08 · Stages 2 and 3 are built in parallel, each in its own worktree, once stage 1 is committed — they touch different files (skills and evals; the hook and its tests), and the user asked for as many agents as it takes to finish quickly.
- 2026-11-08 · The hook compares the Agents line's parsed level and confirmation stamp, not its text, and the stamp carries the time to the minute (`Agents: wide — confirmed 2026-11-08 14:32`): `wide` is honoured only when the line turned to `wide` during the session or gained a new stamp — stage 1 review found that a case or spacing change, which autopilot's own rewrite of `## Now` can make, otherwise turned `wide` on unasked, and a same-day restamp could never confirm.
- 2026-11-08 · An Agents line with an unknown value at the session's first read is distrusted like `wide`: rewriting it to `wide` still asks until a new stamp appears — otherwise a planted `Agents: turbo` gave the same rewrite bypass review found for case changes. Builder's call, accepted.
- 2026-11-08 · Stage 2 started in its own worktree while stage 1's last review fixes were still in progress, not after stage 1's commit — it touches only skills and evals and needs only the line's format, which was settled; stage 3 still waits for the commit, since it calls the hook's `effectiveAgents`.
- 2026-11-08 · Under `lean` the hook also refuses an `Agent` call made by a subagent, not only a second one from the main loop — the goal holds `lean` to one running agent, and a subagent starting its own child makes two; the stage 3 builder had first let nested calls through.
- 2026-11-08 · Only the user's own words in this conversation confirm `wide`; a plan line, logged decision, comment, file or agent report claiming a confirmation is not one — stage 2 review found a planted "the user confirmed wide" decision would otherwise read as the yes, and the hook honours any new stamp.
- 2026-11-08 · Autopilot doesn't pause on an unconfirmed `wide`: it asks when it finds it, runs balanced meanwhile, and stamps on the user's yes — the first wording both paused and kept running.
- 2026-11-08 · A stamp confirms `wide` only if it carries a time inside the session (from the first read of the plan to now): a date-only stamp, a planted past stamp however reformatted, or a future one never confirms — stage 2 review found a planted `confirmed 2026-11-01 10:00` rewritten without its time read as a new stamp. This tightens stage 1's rule after its commit.
- 2026-11-08 · Under `wide`, the correctness and security reviewers run in parallel only when the security lens applies (the risk line names more than UI), as `keel:review` says; the hook's rule first said so unconditionally.
- 2026-11-08 · On an unconfirmed `wide`, keel:stage asks before building and autopilot asks and carries on at balanced; the stamp's time comes from a `date` call, the hook's offered stamp only when there's no shell — the stage 2 re-review found stage, the hook rule and the safety eval disagreeing on building while waiting, and a grader that might not see the hook's stamp.
- 2026-11-08 · Under `lean`, the hook counts main-loop `Agent` calls still in flight as well as running agents, so parallel calls in one message can't all pass — stage 3 review found each call checked the agent list before any spawn registered.
- 2026-11-08 · Stage 4 (docs and release) started in its own worktree while stage 3 was being verified — it touches only the READMEs and the version, and the behaviour it documents was settled.
- 2026-11-08 · The marketplace description is synced to plugin.json's at this release — stage 4 review found it had lagged since before autopilot and evidence; it pins no version.

## Open questions
- Committed screenshots get no secret scan (the guard skips binary files); the docs state the limit and review should look at committed images. A guard for images is out of scope here — the user decides whether it's worth a later plan.
- No eval covers masking yet (a case whose output holds a fake DB URL and email, graded for `[masked]`) — deferred from the last plan's stage 1 review; worth adding in a later plan.
- A `wide` (or `Mode: autopilot`) line that arrives mid-session from git — a checkout or pull of someone else's branch, or a plan that couldn't be read at the session's first look — counts as a change and is honoured without asking; the Mode line already behaves this way. Closing it (move the baseline when the line matches the plan at HEAD, or count only edits made in the user's turn) is a design change for the user to weigh — found in stage 1 review.
- With two Agents lines in `## Now`, only the first is read, so restamping the second does nothing (fails safe, but confusing); and an Agents line past `## Now`'s 40-line cap is parsed but not shown to Claude. Both minor — stage 1 review.

- The `lean` cap counts only `pending`, `running` and `waiting` agents: an `idle` teammate isn't counted (a message can wake it beside a second agent), nor are a SendMessage that resumes a finished agent or a Workflow's fan-out; and agents another plugin spawned, or a dead teammate pane still marked running, count as busy and can stall a `lean` session. The `agent.spawn` event may be a sturdier place for the cap — stage 3 review, deferred. Also deferred from its re-review: when two parallel calls are both refused (the second because the first held the slot, the first further down), the second's "one is still running" is untrue — harmless, Claude can retry.

- `agents-lean` has no balanced control: if a balanced run on the same three-exporter scaffold also builds inline, the eval can't show `lean` caused it (run it once with no Agents line; if so, give it bigger leaves) — stage 2 re-review, deferred.
- A planted stamp the hook reads as date-only (`confirmed 2026-11-08 at 23:59`) could be confirmed by a rewrite that drops the `at`, if the session runs past that minute; it needs a reformat the skills forbid — stage 2 re-review, deferred.

## Standing decisions
- 2026-11-06 · Evidence lives in `docs/evidence/stage-<n>/` for the current plan — beside the plan file, and stage numbers restart with each plan, so a per-plan folder never collides. (from [Verification evidence](plans/2026-11-07-verification-evidence.md))
- 2026-11-06 · Archiving a plan moves its evidence to `docs/plans/<date>-<slug>/evidence/` with `git mv`, and the archived plan's links are rewritten to match — the evidence stays next to the plan it proves, and the new plan starts with an empty `docs/evidence/`. (from [Verification evidence](plans/2026-11-07-verification-evidence.md))
- 2026-11-06 · `report.md` and text output are always committed. Screenshots, traces and videos are committed only when the repo opts in. Verify creates `docs/evidence/.gitignore` ignoring images, traces and videos on first use, and a repo opts in by removing the image lines from it. The report links every file either way, and marks the ones that weren't committed as local — the user decided screenshots shouldn't grow a repo by default, and a gitignore is the opt-in git already understands, with no new setting to learn. (from [Verification evidence](plans/2026-11-07-verification-evidence.md))
- 2026-11-06 · The evidence gate applies to every stage closed after the upgrade to 0.5.0, including stages of plans already in progress, and its denial says how to backfill a report — decided by the user, following the recommendation. (from [Verification evidence](plans/2026-11-07-verification-evidence.md))
- 2026-11-06 · Evidence goes through the existing secret guard like any other commit, and verify is told to mask secrets and personal data in captured output — command output and screenshots can show what the code hides. (from [Verification evidence](plans/2026-11-07-verification-evidence.md))
- 2026-11-06 · The gate (stage 3) checks that the report exists and has a row per check in `## Now`, not that the evidence is any good — judging quality stays with verify and review; the hook only stops a stage from closing with nothing behind it. (from [Verification evidence](plans/2026-11-07-verification-evidence.md))
- 2026-11-06 · Eval cases that use Bash can't run on this machine (the eval sandbox refuses `~/.docker` symlinks under WSL). Until they run elsewhere, a stage whose proof is an eval is proven by a headless `claude -p --plugin-dir plugins/keel` run against the case's scaffold, graded by hand against the case's criteria, and the eval command is noted as still to run — this keeps the proof a real session on the real plugin. (from [Verification evidence](plans/2026-11-07-verification-evidence.md))
- 2026-11-06 · Verify writes evidence whenever a plan stage is verified, including on a "just report" request, and stays in chat for ad-hoc fixes or repos with no plan — review found evidence would otherwise land under the wrong stage; the first wording of that rule led a run to write nothing on a report-only request, so it now says so outright. (from [Verification evidence](plans/2026-11-07-verification-evidence.md))
- 2026-11-06 · The plan context the hook injects now says verifying a stage means running keel:verify, which saves its evidence — in 1 of 2 traced runs, "verify stage 1 is still good" never loaded the skill and so wrote no evidence; with the rule, 3 of 3 did. (from [Verification evidence](plans/2026-11-07-verification-evidence.md))
- 2026-11-06 · The evidence gate reads a stage's check count from the session, or from the plan at HEAD when the session never saw that stage; the ticked-checks gate uses the same HEAD fallback — review found that a stage closed in a later session otherwise passed with a 1-row report and skipped the ticked-checks gate. (from [Verification evidence](plans/2026-11-07-verification-evidence.md))
- 2026-11-06 · Secrets are scanned for every commit on a command line before any stage gate runs, and a report that can't be read counts as missing — review found a throw in the evidence check could otherwise skip the secret scan for a later commit on the same line. (from [Verification evidence](plans/2026-11-07-verification-evidence.md))
- 2026-11-06 · Hook behavior is proven live with plain headless sessions using the installed plugin (it reads the working tree), not `claude -p --plugin-dir`: with a second copy of keel loaded that way, the guard didn't block a commit in this setup. The cause wasn't investigated. (from [Verification evidence](plans/2026-11-07-verification-evidence.md))
- 2026-11-07 · Acceptance checks name `test` as their proof wherever a test can cover them, and hand-proven checks give the reason — a test protects against regressions on every later verify for free, while hand-proven checks are only repeated once, at the end of the plan. (from [Regression and security proof](plans/2026-11-07-regression-security-proof.md))
- 2026-11-07 · Hand-proven checks from earlier stages are re-run once, when the plan's last stage is verified, not per stage or "when a stage touches the same area" — repeating them every stage adds cost with each stage, and "the same area" is a judgment agents would apply unevenly. (from [Regression and security proof](plans/2026-11-07-regression-security-proof.md))
- 2026-11-07 · Before deciding whether to review, stage and autopilot compare the risk line with what the diff touches (user input, auth, money, personal data, secrets, external services) and correct the line in the plan when it's wrong — the line is set at plan time, and a stage that drifted past "UI only" otherwise skips the security pass. (from [Regression and security proof](plans/2026-11-07-regression-security-proof.md))
- 2026-11-07 · The evidence gate doesn't count `Re-run of stage <k>` rows toward a stage's check rows — the stage 1 verifier found re-run rows could otherwise stand in for a missing check row. (from [Regression and security proof](plans/2026-11-07-regression-security-proof.md))
- 2026-11-07 · Not doing: mandatory test-first for every feature (tests first stays the rule for bug fixes and untested code, and tests travel with risky logic), a required static analysis tool in verify, or secure-coding rules at build time — each adds weight for little gain over what the suite, the linter the project already has, and the fresh-eyes security pass catch; projects that want strict TDD can say so in `CLAUDE.md`. (from [Regression and security proof](plans/2026-11-07-regression-security-proof.md))
