# Standing decisions

- 2026-11-06 · Evidence lives in `docs/evidence/stage-<n>/` for the current plan — beside the plan file, and stage numbers restart with each plan, so a per-plan folder never collides. (from [Verification evidence](plans/2026-11-07-verification-evidence.md))
- 2026-11-06 · Archiving a plan moves its evidence to `docs/plans/<date>-<slug>/evidence/` with `git mv`, and the archived plan's links are rewritten to match — the evidence stays next to the plan it proves, and the new plan starts with an empty `docs/evidence/`. (from [Verification evidence](plans/2026-11-07-verification-evidence.md))
- 2026-11-06 · `report.md` and text output are always committed. Screenshots, traces and videos are committed only when the repo opts in. Verify creates `docs/evidence/.gitignore` ignoring images, traces and videos on first use, and a repo opts in by removing the image lines from it. The report links every file either way, and marks the ones that weren't committed as local — the user decided screenshots shouldn't grow a repo by default, and a gitignore is the opt-in git already understands, with no new setting to learn. (from [Verification evidence](plans/2026-11-07-verification-evidence.md))
- 2026-11-06 · The evidence gate applies to every stage closed after the upgrade to 0.5.0, including stages of plans already in progress, and its denial says how to backfill a report — decided by the user, following the recommendation. (from [Verification evidence](plans/2026-11-07-verification-evidence.md))
- 2026-11-06 · Evidence goes through the existing secret guard like any other commit, and verify is told to mask secrets and personal data in captured output — command output and screenshots can show what the code hides. (from [Verification evidence](plans/2026-11-07-verification-evidence.md))
- 2026-11-06 · The gate (stage 3) checks that the report exists and has a row per check in `## Now`, not that the evidence is any good — judging quality stays with verify and review; the hook only stops a stage from closing with nothing behind it. (from [Verification evidence](plans/2026-11-07-verification-evidence.md))
- 2026-11-06 · Eval cases that use Bash can't run on this machine (the eval sandbox refuses `~/.docker` symlinks under WSL). Until they run elsewhere, a stage whose proof is an eval is proven by a headless `claude -p --plugin-dir plugins/keel` run against the case's scaffold, graded by hand against the case's criteria, and the eval command is noted as still to run — this keeps the proof a real session on the real plugin. (from [Verification evidence](plans/2026-11-07-verification-evidence.md))
- 2026-11-06 · Verify writes evidence whenever a plan stage is verified, including on a "just report" request, and stays in chat for ad-hoc fixes or repos with no plan — review found evidence would otherwise land under the wrong stage; the first wording of that rule led a run to write nothing on a report-only request, so it now says so outright. (from [Verification evidence](plans/2026-11-07-verification-evidence.md))
- 2026-11-06 · The plan context the hook injects now says verifying a stage means running keel:verify, which saves its evidence — in 1 of 2 traced runs, "verify stage 1 is still good" never loaded the skill and so wrote no evidence; with the rule, 3 of 3 did. (from [Verification evidence](plans/2026-11-07-verification-evidence.md))
- 2026-11-06 · The evidence gate reads a stage's check count from the session, or from the plan at HEAD when the session never saw that stage; the ticked-checks gate uses the same HEAD fallback — review found that a stage closed in a later session otherwise passed with a 1-row report and skipped the ticked-checks gate. (from [Verification evidence](plans/2026-11-07-verification-evidence.md))
- 2026-11-06 · Secrets are scanned for every commit on a command line before any stage gate runs, and a report that can't be read counts as missing — review found a throw in the evidence check could otherwise skip the secret scan for a later commit on the same line. (from [Verification evidence](plans/2026-11-07-verification-evidence.md))
- 2026-11-06 · Hook behavior is proven live with plain headless sessions using the installed plugin (it reads the working tree), not `claude -p --plugin-dir`: with a second copy of keel loaded that way, the guard didn't block a commit in this setup. The cause wasn't investigated. (from [Verification evidence](plans/2026-11-07-verification-evidence.md))
- 2026-11-07 · Acceptance checks name `test` as their proof wherever a test can cover them, and hand-proven checks give the reason — a test protects against regressions on every later verify for free, while hand-proven checks are only repeated once, at the end of the plan. (from [Regression and security proof](plans/2026-11-07-regression-security-proof.md))
- 2026-11-07 · Hand-proven checks from earlier stages are re-run once, when the plan's last stage is verified, not per stage or "when a stage touches the same area" — repeating them every stage adds cost with each stage, and "the same area" is a judgment agents would apply unevenly. (from [Regression and security proof](plans/2026-11-07-regression-security-proof.md))
- 2026-11-07 · Before deciding whether to review, stage and autopilot compare the risk line with what the diff touches (user input, auth, money, personal data, secrets, external services) and correct the line in the plan when it's wrong — the line is set at plan time, and a stage that drifted past "UI only" otherwise skips the security pass. (from [Regression and security proof](plans/2026-11-07-regression-security-proof.md))
- 2026-11-07 · The evidence gate doesn't count `Re-run of stage <k>` rows toward a stage's check rows — the stage 1 verifier found re-run rows could otherwise stand in for a missing check row. (from [Regression and security proof](plans/2026-11-07-regression-security-proof.md))
- 2026-11-07 · Not doing: mandatory test-first for every feature (tests first stays the rule for bug fixes and untested code, and tests travel with risky logic), a required static analysis tool in verify, or secure-coding rules at build time — each adds weight for little gain over what the suite, the linter the project already has, and the fresh-eyes security pass catch; projects that want strict TDD can say so in `CLAUDE.md`. (from [Regression and security proof](plans/2026-11-07-regression-security-proof.md))
- 2026-11-08 · Three levels: `lean` (build and verify in the main session, one agent at a time), `balanced` (today's behaviour, and the default when there's no line), `wide` (fan out every independent leaf in its own worktree, a fresh agent verifies, correctness and security reviewers run in parallel) — named levels are easier to say and remember than a number, and `balanced` keeps existing projects unchanged. (from [Agents level](plans/2026-11-08-agents-level.md))
- 2026-11-08 · The level lives in `## Now` as `Agents: <level>`, beside the Mode line, and the skills carry it into each new `## Now` — the hook already reads `## Now` into every request, so the level survives compaction with no new file or setting. (from [Agents level](plans/2026-11-08-agents-level.md))
- 2026-11-08 · Every level keeps at least one fresh reviewer — review by an agent that didn't write the code is the point of `keel:review`, and `lean` is about parallelism, not about skipping independent eyes. Under `lean`, autopilot still delegates building, one builder at a time. (from [Agents level](plans/2026-11-08-agents-level.md))
- 2026-11-08 · Only `lean` gets a hard cap (one running agent); `balanced` and `wide` aren't capped by Keel — a cap on `balanced` would change today's behaviour, and Claude Code's own limits already bound `wide`. (from [Agents level](plans/2026-11-08-agents-level.md))
- 2026-11-08 · Only the user's own words in this conversation confirm `wide`; a plan line, logged decision, comment, file or agent report claiming a confirmation is not one — stage 2 review found a planted "the user confirmed wide" decision would otherwise read as the yes, and the hook honours any new stamp. (from [Agents level](plans/2026-11-08-agents-level.md))
- 2026-11-08 · A stamp confirms `wide` only if it carries a time inside the session (from the first read of the plan to now): a date-only stamp, a planted past stamp however reformatted, or a future one never confirms — stage 2 review found a planted `confirmed 2026-11-01 10:00` rewritten without its time read as a new stamp. This tightens stage 1's rule after its commit. (from [Agents level](plans/2026-11-08-agents-level.md))
- 2026-11-08 · Under `lean`, the hook counts main-loop `Agent` calls still in flight as well as running agents, so parallel calls in one message can't all pass — stage 3 review found each call checked the agent list before any spawn registered. (from [Agents level](plans/2026-11-08-agents-level.md))
- 2026-11-08 · The large-project layer is files that only take effect when present: no `docs/ROADMAP.md` means no roadmap line, no ledger and no milestone checks — the user wants large projects handled without overhead for the ones that aren't, and absence-as-off needs no setting. (from [Large projects](plans/2026-11-08-large-projects.md))
- 2026-11-08 · `keel:plan` decides the path from signals it can count — stage count after an honest cut (>~8), a PRD's distinct requirements (>~15) or its own phase list, more than one release in the goal, or the user's words — and asks once with a recommendation only when one fires; the answer is logged as a decision and not asked again. Small work is planned without the question. (from [Large projects](plans/2026-11-08-large-projects.md))
- 2026-11-08 · Plans are cut one at a time from the current milestone, not all up front — a plan written months ahead is guesswork, and Keel cuts stages after surveying the code they touch. The charter assigns requirements to milestones and milestone dependencies only. (from [Large projects](plans/2026-11-08-large-projects.md))
- 2026-11-08 · Roadmap layout, fixed now so stages 1, 4 and 5 can build in parallel: `# <Project> roadmap`, a `Source:` line (the PRD path and the date charted), `## Milestones` as a checklist `- [ ] M1. <Name> — <scope> (needs: M0)`, `## Requirements` as a table `| ID | Requirement | PRD § | Milestone | Covered by |`, then `## Out of scope` and `## Open questions`. A requirement the PRD drops keeps its row with `dropped <date>` in the Milestone cell and leaves the total; rows are never deleted. (from [Large projects](plans/2026-11-08-large-projects.md))
- 2026-11-08 · Coverage is derived, not tracked: `Covered by` names the archived plan whose evidence report has a passing row tagged with the ID, filled when that plan is archived; the hook only counts filled cells — a hand-kept status column drifts, and counting a table is cheap enough for every request. (from [Large projects](plans/2026-11-08-large-projects.md))
- 2026-11-08 · Requirement tags go at the end of a check, `(req: SEC-01)` — the stage-close parser reads a leading number as a stage number, and a tag first in an evidence row could look like a re-run row. (from [Large projects](plans/2026-11-08-large-projects.md))
- 2026-11-08 · Locked decisions from a PRD go to `CLAUDE.md`, not the plan — they bind every session and subagent, and `CLAUDE.md` already reaches them. (from [Large projects](plans/2026-11-08-large-projects.md))
- 2026-11-08 · The hook adds no roadmap line when every milestone is ticked, or when there's no plan (the line rides in the plan section) — starting the next body of work is `keel:plan`'s job, and a stale "all done" line would sit in every request. A `Covered by` cell holding only a dash counts as empty, since that's how markdown tables commonly write an empty cell; charter and archive (stages 4–5) should still leave it blank. (from [Large projects](plans/2026-11-08-large-projects.md))
- 2026-11-08 · Stage 1's verify runs in the main session, and that run writes the report itself: subagents here can't write report `.md` files, and the user chose this over saving the fresh verifier's text on its behalf. The fresh verifier's mutation evidence stays alongside it. (from [Large projects](plans/2026-11-08-large-projects.md))
- 2026-11-08 · `Covered by` holds a link to the archived plan, relative to `docs/` (`[<plan name>](plans/<date>-<slug>.md)`), whether the archive step (stage 5) or the charter's backfill (stage 4) fills it — one form, so a reader can follow it and the milestone close can check the plan exists; the stage 4 builder had used the bare name. (from [Large projects](plans/2026-11-08-large-projects.md))
- 2026-11-08 · The roadmap's count is across the whole ledger, not the current milestone's rows (`M1 14/46` reads as "at M1, 14 of the project's 46 covered") — it matches the plan's example and the "how far along is the project" question; the milestone close (stage 5) checks the milestone's own rows. (from [Large projects](plans/2026-11-08-large-projects.md))
- 2026-11-08 · Stage 3 also fixes the built-in outward check's parser: `{ git push; }`, `if …; then git push`, `sudo -u bob git push`, `timeout 60 git push` and `bash -c "git push"` all got past it under autopilot (pre-existing, found by stage 3's security review). It's the guard this stage builds on, so it's in scope; when unsure, the parser leans toward holding — a false hold costs a pause, a miss costs a push. (from [Large projects](plans/2026-11-08-large-projects.md))
- 2026-11-08 · Project rules are sticky for the session: the hook keeps every rule it has seen since the session started, so deleting a `Keel outward:` line mid-run doesn't lift it — removing a rule takes a new session. The agent could otherwise edit `CLAUDE.md` through Bash and then run the command. (from [Large projects](plans/2026-11-08-large-projects.md))
- 2026-11-08 · Autopilot never crosses into a plan the user hasn't seen: at a milestone close it closes the milestone, cuts the next plan, and stops for the user's yes before building it — the stage 5 builder had autopilot carry on when the Goal "reached past" the milestone, which stage 5's security review showed lets the agent write and run its own plans, risk lines included. Keel's rule stands: autopilot runs a plan the user approved, never one it wrote alone. (from [Large projects](plans/2026-11-08-large-projects.md))
- 2026-11-08 · Ticking a milestone in `docs/ROADMAP.md` is gated by the hook like a stage close: the commit is refused unless the milestone's evidence (`milestone-<ID>.md`) has a row per non-dropped requirement of that milestone — the close was otherwise instructions only. (from [Large projects](plans/2026-11-08-large-projects.md))
- 2026-11-08 · The outward check is a guardrail against an agent pushing by mistake, not a sandbox against one trying to: it reads the command line, closes the realistic ways a push hides (substitutions, line continuations, heredocs, stdin-fed shells, wrappers, run-time-built heads) and lists the rest as limits in the README (pushes from inside scripts or interpreters, aliases defined elsewhere, git subcommands that push under another name) — a full shell interpreter isn't worth its weight, and the stage 3 parser re-review found no false holds on everyday commands to trade against. (from [Large projects](plans/2026-11-08-large-projects.md))
- 2026-11-08 · At archive, an ID counts as taken on by the plan when it's tagged on one of the plan's checks or named in its Goal, and it's filled only with a passing tagged row in that plan's own stage reports and no failing re-run after it — a finished plan's `## Now` no longer holds its checks, so the Goal is the durable record; the evidence row is still required. (from [Large projects](plans/2026-11-08-large-projects.md))
- 2026-11-08 · `keel:charter` runs only when the user asks to chart (or set up a roadmap, or re-chart) or says yes to `keel:plan`'s scale question; a request to plan or build goes through `keel:plan`, which asks first — the final regression run found the charter's "a project too big for one plan" trigger taking a plain "plan the build" request and charting without asking. (from [Large projects](plans/2026-11-08-large-projects.md))
- 2026-11-08 · The hook reads at most 256K characters and 4,000 lines of the roadmap and cuts milestone names at 60 characters — it runs on every request, and a ledger past the cap is undercounted rather than slowing each one. (from [Large projects](plans/2026-11-08-large-projects.md))
- 2026-11-08 · Project risk rules only add: Keel's built-in outward check runs first and unconditionally, and the project list is consulted only when it found nothing; there's no allow or negation syntax — a cloned repo's `CLAUDE.md` mustn't loosen a guard, the same reasoning that keeps a `wide` line from raising spend unasked. (from [Large projects](plans/2026-11-08-large-projects.md))
- 2026-11-08 · Standing decisions move to `docs/decisions.md` once more than ten would carry forward, with one pointer line left in the plan; below that they stay in the plan — small projects keep one file, and the `next-feature` eval keeps grading the plan. (from [Large projects](plans/2026-11-08-large-projects.md))
- 2026-11-08 · Deferred, not built: a "decide" stage type, more than one active plan, and a debug workflow — a decision can be a stage whose check is a prototype and a logged decision; parallel plans bring back state sync; the built-in debugging tools already cover investigation. (from [Large projects](plans/2026-11-08-large-projects.md))
- 2026-11-09 · An approval is the user's message opening with yes, yep, go, approve, approved, proceed or build it, then the end of the message or punctuation (`yes, …`, `Go.`), or a message opening with `/keel:approve`. "go ahead and tell me…" doesn't count, since the word is followed by a space and more text. The hook can't read intent, and a narrow, stated rule that the notices spell out is better than a guess. A "yes, but first…" still releases the stage; the user did open with yes. (from [Explicit approval and secret formats](plans/2026-11-09-explicit-approval-secret-formats.md))
- 2026-11-09 · `/keel:approve` is a skill so that it shows up as a command, but the hook clears the stage only from the user's prompt text, never when the skill runs. Claude can invoke a skill itself, so a skill-triggered clear would let it approve its own hold. (from [Explicit approval and secret formats](plans/2026-11-09-explicit-approval-secret-formats.md))
- 2026-11-09 · No short-password detection. A rule that flags `password = "hunter2"` would also fire on fixtures, docs and examples, and a guard people learn to bypass protects nothing. The hard-coded credential rule keeps its 24-character floor. (from [Explicit approval and secret formats](plans/2026-11-09-explicit-approval-secret-formats.md))
- 2026-11-09 · The evidence header rule applies only under `docs/evidence/`, where verify already must mask these headers. Elsewhere a header line is ordinary code (`Authorization: Bearer ${token}`). (from [Explicit approval and secret formats](plans/2026-11-09-explicit-approval-secret-formats.md))
- 2026-11-09 · The approval rule stays as planned (an approval word opening the reply, or `/keel:approve`), on the user's word after weighing a looser "word anywhere in a short reply" — the looser rule would count "should I approve this?". (from [Explicit approval and secret formats](plans/2026-11-09-explicit-approval-secret-formats.md))
- 2026-11-09 · `keel:approve` sets `disable-model-invocation: true`, the only keel skill that does: Claude can't run it at all, which backs the rule that only the user's typed prompt approves (the hook ignores a self-invoked skill anyway). (from [Explicit approval and secret formats](plans/2026-11-09-explicit-approval-secret-formats.md))
- 2026-11-09 · Stage 1 review: a plan paused on a risky stage is now held like a driving one (edits outside the plan and builder agents denied until approval) while autopilot is armed in the session. Autopilot's own procedure pauses on a risky stage, and the pause had switched the guard off, so the approval rule protected nothing. Pre-existing, but it's this stage's guard, so it's in scope. (from [Explicit approval and secret formats](plans/2026-11-09-explicit-approval-secret-formats.md))
- 2026-11-09 · Agent tampering with its own plan (dropping a word from the risk line, reusing an approved stage line for a later stage, removing the Mode line) and writes through Bash stay out of the hold, as with the outward check (2026-11-08): the hold is a guardrail against building a sensitive stage by mistake, not a sandbox against an agent trying to. They're listed as open questions. (from [Explicit approval and secret formats](plans/2026-11-09-explicit-approval-secret-formats.md))
- 2026-11-09 · Stage 2 builder's calls, kept: `Proxy-Authorization` is checked with the other headers; in evidence a placeholder value (`$TOKEN`, `${…}`, `{{…}}`, `<…>`) counts as hidden like `[masked]`, so a recorded `curl -H "Authorization: Bearer $TOKEN"` passes; a bearer token needs a digit and a letter in its 20+ characters, so all-caps placeholders aren't flagged (a real token with no digit would be missed, which is rare); ~~a Cookie header passes only when every value is hidden, a Set-Cookie only its first pair (the rest are attributes)~~ — replaced by the review decision below: every cookie pair is checked, Set-Cookie attributes skipped, since a folded Set-Cookie line carried a session cookie past the first pair. (from [Explicit approval and secret formats](plans/2026-11-09-explicit-approval-secret-formats.md))
- 2026-11-09 · Stage 2 review: in evidence, a header is refused only when its value, with `[masked]` and placeholders removed, still holds a credential-like run (16+ token characters with a letter and a digit). Without that, the rule flagged prose, markdown table rows, grep output of source and `undefined`/`null`, and the easy way out was `keel:allow-secret`. A short real cookie value is missed, consistent with no short-password detection. (from [Explicit approval and secret formats](plans/2026-11-09-explicit-approval-secret-formats.md))
- 2026-11-10 · Version bumps: a new skill or feature is a minor bump; the marketplace entry has no version, so plugin.json's is what tells installed copies to update. (from [Quick-fix path](plans/2026-11-10-quick-fix-path.md))
- 2026-11-10 · The fix bar: a bug fix qualifies only in UI-only code; CLI output text counts as UI; dependencies, CI, deploy and container config, build or env config that changes what reaches the client, security headers, rendering user-supplied content and the project's `Keel risk:` words miss it; several fixes toward one outcome are a stage; a fix needs no uncommitted stage work in the tree. When Claude judges a request fits, it says so in one line, naming why, before the first edit, then goes on without waiting. (from [Quick-fix path](plans/2026-11-10-quick-fix-path.md))
- 2026-11-10 · `## Fixes` stays with the plan it was logged under and is archived with it; a new plan starts without one. (from [Quick-fix path](plans/2026-11-10-quick-fix-path.md))
